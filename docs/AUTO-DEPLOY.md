# פריסה אוטומטית — מה מתעדכן לבד ומה לא יכול

מ-`.github/workflows/deploy.yml`. כל דחיפה לענף העבודה פורסת רק את מה שהשתנה.

| מה השתנה | לאן זה מגיע | תוך כמה זמן |
|---|---|---|
| `theme/` | האתר החי | שנייה |
| `mobile-app/` | האפליקציה, כעדכון OTA | דקה |
| `assistant-server/` | העוזר, ב-production | דקה |
| נתוני קטלוג (מוצרים, מחירים) | החנות ישירות דרך ה-API | מיד, בלי פריסה |

---

## מה שצריך להגדיר פעם אחת

### 1. Theme Access — הדרך לפרוס תבנית

זה החלק שדרש פתרון. `themeFilesUpsert` דרך ה-API מחזיר:

> requires `write_themes` **and an exemption from Shopify to modify theme files**

כלומר גם הרחבת ההרשאות של האפליקציה `Shilo Image Tools` לא הייתה מספיקה — נדרש פטור מיוחד מ-Shopify. **Theme Access היא אפליקציה רשמית של Shopify שנבנתה בדיוק לזה**, היא מנפיקה סיסמה ל-`shopify theme push` בלבד, ואינה נוגעת בהרשאות של שום אפליקציה אחרת.

1. להתקין [Theme Access](https://apps.shopify.com/theme-access) בחנות
2. `Add password` עם המייל שלך — Shopify שולחת את הסיסמה במייל
3. הסיסמה נכנסת כסוד ב-GitHub

היקף ההרשאה של הסיסמה הזאת הוא קבצי תבנית בלבד. היא לא יכולה לגעת במוצרים,
בהזמנות או בלקוחות, וזה בדיוק ההבדל בינה לבין הרחבת טוקן קיים.

### 2. Expo — לאפליקציה ולעוזר

`expo.dev → Account settings → Access tokens → Create token`. אותו טוקן משמש
לשניהם.

### 3. הסודות ב-GitHub

`Settings → Secrets and variables → Actions → New repository secret`:

```
SHOPIFY_CLI_THEME_TOKEN   הסיסמה מ-Theme Access
SHOPIFY_STORE             3007b3-4.myshopify.com
SHOPIFY_THEME_ID          148378648655        ← shilov8theme, התבנית החיה
EXPO_TOKEN                הטוקן מ-expo.dev
```

**`SHOPIFY_THEME_ID` הוא 148378648655 ולא 148375371855.** HANDOFF §3 נוקב במזהה
השני, וזו התבנית הלא נכונה — הפער הזה כבר גרם פעם אחת לכתיבת שינוי לתבנית שאינה
חיה, ואיש לא ראה אותו באתר.

## שתי שמירות שבנויות בצינור, ולמה

### התבנית נבדקת לפני שהיא נדחפת

`shopify theme check --fail-level error` רץ לפני הדחיפה. ליקוויד שבור מגיע לאתר
החי בשנייה שהוא נדחף ואין שלב ביניים שיתפוס אותו, אז זה השלב.

הדחיפה היא `--nodelete`. `settings_data.json` נערך בממשק ואינו מנוהל בריפו, ובלי
הדגל הזה כל דחיפה הייתה מוחקת את ההגדרות שבעל החנות שינה בעצמו.

### עדכון OTA שלא יכול להגיע — נכשל במקום להתפרסם

הפרויקט על `runtimeVersion: { policy: fingerprint }`. שינוי שנוגע בנייטיב — תוסף,
הרשאה, גרסת SDK, `app.json` — מזיז את ה-fingerprint, **ואז `eas update` מפרסם
עדכון שאף בילד קיים אינו יכול לקבל.** הפקודה מצליחה, הלוג נראה תקין, ואף מכשיר
לא רואה דבר.

זה קרה כאן: הפעלת R8 הזיזה את ה-fingerprint מ-`1e3cc308` ל-`09914647`.

לכן הצינור משווה את ה-fingerprint הנוכחי לזה שכבר פורסם בערוץ, ואם הוא זז הוא
**נכשל בהודעה מפורשת** במקום לפרסם עדכון מת. במקרה כזה נדרש `eas build` והגשה
לחנויות — וזה הדבר האחד שלא יכול להיות אוטומטי, כי אפל וגוגל בודקות.

### העוזר נבדק אחרי הפריסה

`eas deploy --prod` **לבדו** יוצר פריסה בלי משתני הסביבה ומקדם אותה, והעוזר החי
מחזיר 503 על כל בקשה. זה קרה בפועל והוריד את העוזר עד שתוקן. הצינור מריץ
`--prod --environment production` יחד, ואחרי הפריסה שולח שאלה אמיתית לכתובת החיה
ונכשל אם התשובה ריקה או שגיאה — כי פריסה שהצליחה אינה עוזר שעובד.

## מה שלא יכול להתעדכן לבד, ולמה

**שינוי נייטיב באפליקציה.** תוסף חדש, הרשאה, שינוי ב-`app.json`, גרסת SDK. אלה
דורשים `eas build` ואז הגשה ל-App Store ול-Play, ושם יש בדיקה אנושית. הצינור
יעצור עם הודעה ברורה במקום להעמיד פנים שזה עלה.

**מדיניות החנות.** ל-Admin API אין הרשאת כתיבה למדיניות משפטית, ולכן מדיניות
ההחזרים נערכת בממשק. זה נעשה כבר.

**קטגוריות, מחירים ותמונות של מוצרים** אינם פריסה אלא נתונים, והם מגיעים לחנות
דרך ה-API ברגע שהסקריפט רץ — האתר והאפליקציה שניהם קוראים מאותה חנות, כך שאין מה
לסנכרן ביניהם. זה נכון גם היום.
